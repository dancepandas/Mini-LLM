# `eval/` —— 评测

用于评估训练各阶段产出的模型。**评测不是走过场** ——
它是发现"训练代码有 bug 但 loss 曲线正常"这类问题的唯一手段。

---

## 文件一览

| 文件 | 作用 |
|---|---|
| `ppl.py` | 困惑度（Perplexity）评测 |

---

## `ppl.py` —— 困惑度

```bash
# 自动找最新模型
python eval/ppl.py

# 指定模型
python eval/ppl.py --model checkpoints/sft/final.pt
python eval/ppl.py --model checkpoints/pretrain/step_0005000.pt

# 调参
python eval/ppl.py --split val --n-batches 100
python eval/ppl.py --out eval_result.json
```

### 什么是困惑度

```
PPL = exp(平均交叉熵损失)
```

直观理解：模型在每一步平均要在多少个候选词里"犹豫"。
`PPL=100` 意味着模型平均认为有 100 个词同样可能。

### 参考量级（中文语料）

| 阶段 | 困惑度 | 含义 |
|---|---:|---|
| 随机初始化 | ≈ 32768 | 等于词表大小，完全没学到 |
| 训练早期 | 100 ~ 200 | 学到了一些 |
| 训练充分 | 15 ~ 30 | 掌握了语言规律 |
| SFT 之后 | 10 ~ 25 | 分布不同，可能略有浮动 |

脚本会根据结果给出判断，避免需要记住这些数字。

### 为什么要采样而不是跑完整验证集

验证集有 200 万 token，跑完要几十秒。
采样 50 个 batch（约 20 万 token）已经能让标准误差降到可接受范围。
用 `--n-batches` 调整。

## 评测的正确用法（重要）

### 1. 各阶段都要评测，不要只看最终结果

```
预训练后   → ppl 应该在 20~35（学习语言规律）
SFT 后     → ppl 可能略升（数据分布变了），但对话能力应该显著提升
RL 后      → ppl 通常进一步上升（策略偏离 base），但任务成功率应该提升
```

**如果 SFT 后 ppl 暴涨**（比如从 25 涨到 200），说明学习率太大或者训练步数过多，
模型发生了灾难性遗忘 —— 把预训练学到的语言能力冲掉了。
这是 SFT 最典型的事故。

### 2. 困惑度低 ≠ 对话能力好

困惑度衡量的是"预测下一个 token"的能力。
一个模型可以在困惑度上表现很好，但完全不会按指令回答 ——
因为它是在续写，不是在对话。

**判断"能不能对话"必须实际跑 `scripts/06_chat.py` 聊几句。**
困惑度只是辅助指标。

### 3. 和 loss 曲线交叉验证

训练日志里的 loss 是**训练集**上的（而且是滑动平均，有滞后）。
验证集 ppl 是独立采样的。如果两者走势背离：
- 训练 loss 降但验证 ppl 升 → 过拟合
- 两者都正常但对话效果差 → 检查 chat template 是否一致

## 后续可以补充的评测

当前只实现了困惑度，因为它是最基础的。如果要更全面地评估，可以补充：

| 类型 | 说明 | 难度 |
|---|---|---|
| 选择题基准 | C-Eval / CMMLU 的中文选择题，看准确率 | 中 |
| 任务成功率 | 对 RL 阶段，看数学题的正确率变化 | 低（`05_rl_grpo.py` 里已有统计） |
| 人工对话评估 | 实际聊，按"是否切题/是否通顺/是否有用"打分 | 低但主观 |

对 0.3B 这个量级，**坦诚地说：选择题基准的分数会很低**（接近随机猜）。
这不是训练失败，而是模型容量和预训练量的客观限制。
更有意义的评估是：困惑度是否正常下降、能否按格式对话、
RL 阶段的任务成功率是否提升。
