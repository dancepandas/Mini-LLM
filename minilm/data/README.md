# `minilm/data/` —— 数据管线

从魔塔社区下载中文语料，清洗、分词，最终打包成训练用的二进制 memmap。

```
modelscope.py    流式下载（分块并行 + 断点续传）
     ↓
clean.py         清洗：长度过滤、乱码过滤、精确去重
     ↓
build_bin.py     分词 → 拼接 → 写入 uint16 memmap
     ↓
dataset.py       训练时从 memmap 随机裁剪出批次
```

---

## 为什么要把数据预处理成二进制

**如果训练时在线分词**：每个 step 都要跑一遍 BPE。BPE 是 CPU 密集的逻辑，
在 4618 tok/s 的训练吞吐下会成为严重瓶颈 —— GPU 会一直空等 CPU，
实际吞吐可能掉到几百 tok/s。

**预分词后**：训练时只需要对一个扁平数组做一次内存切片，开销可忽略。
这是 nanoGPT 等项目的标准做法。

**代价**：磁盘。2B tokens × 2 字节（uint16）= 约 4GB，完全可以接受。

## `modelscope.py` —— 魔塔下载

### 网络事实（实测，很重要）

| 事实 | 说明 |
|---|---|
| **魔塔不走代理** | 必须直连。走代理反而会变慢或卡死 |
| 单连接约 1.5 MB/s | 而且不稳定，有时会卡到 0 |
| **分块并行可达 6 MB/s** | HTTP Range + 8 并发 |
| 列出文件树正确端点是 `/repo/tree` | `/oss/tree` **返回 200 但数据为空**，极具误导性 |

### 代理的坑（踩过）

**光清环境变量不够**。Windows 上 `urllib` 还会去读**系统级代理设置**
（注册表里的 WinINET 配置），如果系统代理处理不了该站点，
会报 `SSL record layer failure` 这类底层错误。

必须显式传一个空的 ProxyHandler：

```python
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
```

代码里 `_request_json()` 和所有下载函数都做了这个处理。

### 两种并发下载（互补）

| 函数 | 场景 | 原理 |
|---|---|---|
| `download_files_parallel()` | **很多小文件**（如 Fineweb 的 9745 个分片） | 每文件一线程 |
| `download_file_chunked()` | **一个巨大文件**（如 8.28GB 的 jsonl） | HTTP Range 切成 64MB 块并行下载，最后拼接 |

`download_files_chunked_parallel()` 是上层封装：**逐个文件处理，
每个文件内部开 N 个并发**。为什么不是把所有块丢进一个大线程池 ——
那会让并发数失控（10 文件 × 8 块 = 80 连接），大概率被服务端限流。

分块下载的可靠性设计：
- 每块写独立的 `.part` 文件（避开并发写同一句柄，Windows 上会出错）
- 已完成块跳过（断点续传）
- 最后按序拼接，**校验总大小**，不符就报错（避免拼出损坏文件）

### 文件列表 API 的坑

`list_files()` 优先用**手写 HTTP 分页**而不是 SDK。原因：

实测 `HubApi.get_dataset_files()` 在 `page_size=1000` 时
**只返回第一页就停了**（拿到 999 个文件），
而 Fineweb-Edu-Chinese-V2.1 实际有 29286 个文件。

这种"成功但结果不全"的行为非常危险 —— 不报错，
但会导致只看到字母序靠前的分片。自己翻页虽然朴素，但行为完全可控。

## `clean.py` —— 文本清洗

### 为什么只做轻量清洗

重型手段（MinHash 跨文档去重、质量分类器打分）在这里不划算：

1. 我们用的语料（minimind 数据集、维基过滤版）**本身已过上游清洗**
2. MinHash 需要几十 GB 内存和大量 CPU 时间，在 5 天训练预算下不划算
3. 保持流程可理解、可调试，比追求极致语料质量更重要

### 实际做的过滤

| 过滤项 | 阈值 | 目的 |
|---|---|---|
| 最小长度 | 200 字符 | 过滤标题、残句等低信息量文本 |
| 最大长度 | 100,000 字符 | 超长文档截断而非丢弃 |
| 汉字占比 | ≥ 30% | 过滤名义中文实为英文/代码的文档 |
| 符号占比 | ≤ 30% | 过滤分隔线、乱码 |
| 数字占比 | ≤ 50% | 过滤表格、纯数字列表 |
| 重复行占比 | ≤ 30% | 过滤模板页（导航栏/页脚反复出现） |

**处理顺序是刻意安排的**：先做廉价的字符串替换，
再做需要遍历全文的统计，最后才做需要逐行处理的重复度检测。
这样大部分垃圾在早期就被廉价地滤掉了。

### `Deduplicator` —— 精确去重

只保存文档的 **64 位哈希**（8 字节），不保存文档本身。
1000 万篇文档约占 80MB 内存。
64 位空间下 1000 万篇的碰撞概率约 2.7e-6，可以忽略。

用 `hashlib.blake2b` 而不是内置 `hash()` —— 后者有随机化，跨进程不一致。

### `format_clean_stats()` 会给出健康度判断

保留率 < 30% 说明过滤太严；> 95% 说明可能没起作用。
这个提示很重要，避免"清洗完才发现保留率极低"的事后发现。

## `build_bin.py` —— 分词与打包

`TokenizeWriter` 边分词边写文件：

1. **内存恒定**：token 先在缓冲区累积（默认 800 万），攒够就刷盘
2. **批量分词**：用 `tokenizer.encode_batch()`（内部是 Rust + 多核并行），
   比逐条快数倍
3. **原子性**：写临时文件，完成后 `os.replace()` 重命名

用 **uint16** 存储：词表 32768 < 65536，比 int32 省一半空间和带宽。

> ⚠️ `build_bin` 里会检查词表是否超过 65536。
> 超了的话 numpy 写入时会**静默截断** token id，导致训练数据损坏。
> 这是为了避免"训了 5 天才发现数据是坏的"。

## `dataset.py` —— 训练数据读取

### `MemmapDataset`

**核心思想**：预训练数据是一个超长的 token 数组。
训练样本 = 在数组里随机取一个起点，往后读 `seq_len + 1` 个 token。

这是 nanoGPT 的做法，优点：
- **零预处理开销**：取样本就是内存切片，O(1)
- **没有 padding**：所有样本都是满长度
- **文档边界自然处理**：直接拼接不同文档，用 `<|endoftext|>` 分隔
- **可断点续训**：只需记录 step 数，数据顺序由随机种子决定

用 `np.memmap` 而不是 `np.fromfile`：
前者让 OS 按需载入页，不会一次性占用 4GB 常驻内存。

**为什么 y 是 x 右移一位**：语言模型任务是"给定前 t 个 token 预测第 t+1 个"。
一个长度为 seq_len 的窗口能产出 seq_len 个训练信号，
这是 Transformer 并行训练的威力所在。

**为什么不用 DataLoader**：
1. Windows 上多进程默认是 spawn，启动开销大，而数据在 memmap 里
   根本不需要多进程预取
2. 训练循环需要精确控制每个 micro-batch，自己实现更直接
3. 少一层抽象就少一个出问题的地方

### `PackedSFTDataset`

SFT 专用。和预训练不同，每个 token 有"该不该算 loss"的区别。
padding 的位置 label 必须是 `-100`，否则模型会学着预测 padding token。

### ⚠️ 许可证

`minimind_dataset` 是 **CC-BY-NC-4.0（非商用）**。
学习研究没问题，商用必须换源（如 `swift/Chinese-Qwen3-235B-...`，Apache-2.0）。

### 已知数据局限

minimind 的预训练数据是**短问答/指令对拼接**的短文（平均约 215 字符/条），
不是维基/书籍那种长文档。后果是模型「会聊天但知识面窄」。
掺入维基长文本是缓解手段。
